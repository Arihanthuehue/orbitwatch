## DATABASE DESIGN (MySQL, follows the project report, BCNF)

Follow the report's entities, attributes, constraints, FKs, and ON DELETE rules. Where real data forces a justified change, make the change and document it in `docs/DESIGN_DECISIONS.md` (e.g., real debris often has no measured size, so `size_meters` is nullable with an `rcs_size_class` column and an `is_estimated` flag).

**Tables (at minimum):**
- `TRACKING_STATION` (Station_ID PK, Station_Name, Location_Country, Latitude CHECK -90..90, Longitude CHECK -180..180, Sensor_Type, source_url)
- `SATELLITE` (Satellite_ID PK, NORAD_ID UNIQUE, intl_designator UNIQUE, Satellite_Name, Owner_Agency, Launch_Date, Operational_Status CHECK IN ('Active','Inactive','Deorbiting','Destroyed'), Orbital_Altitude_KM CHECK >0, Inclination_Deg CHECK 0..180, plus orbital elements needed for SGP4)
- `DEBRIS` (Debris_ID PK, NORAD_ID UNIQUE, Object_Name NOT NULL, Size_Meters, rcs_size_class, Mass_KG, Velocity_KMS CHECK >0, Apogee_KM, Perigee_KM, Inclination_Deg CHECK 0..180, orbit_class, Station_ID FK ON DELETE SET NULL, parent info, orbital elements for SGP4)
- `COLLISION_EVENT` (Event_ID PK, Satellite_ID FK ON DELETE CASCADE, Debris_ID FK ON DELETE CASCADE, Event_Timestamp (TCA), Miss_Distance_KM CHECK >=0, Relative_Velocity CHECK >0, Collision_Risk_Prob CHECK 0..1, source ENUM('SOCRATES','computed','manual'))
- `OBSERVATION` (fixes the gap between the ER diagram and the schema: the station-monitors-object relationship; Observation_ID PK, Station_ID FK, exactly one of Satellite_ID/Debris_ID via CHECK, observed_at, position/state fields). Indexed heavily.
- `ORBIT_STATE_HISTORY` (historical trajectory versioning: every orbital-element update keeps the old record with epoch; this is the research gap from Section 5)
- `DEBRIS_LINEAGE` (fragment parent-child tree with self-referencing FK or parent-event table, populated from real breakup events such as Fengyun-1C, Cosmos 2251/Iridium 33, Cosmos 1408)
- `APP_USER`, `ROLE`, `AUDIT_LOG`, `ALERT`, `TEST_CASE`, `TEST_RUN`, `DATA_SYNC_LOG`

**Required DB features (all must be real and demonstrable):**
- **Views:** `v_high_risk_events`, `v_debris_catalog`, `v_satellite_exposure`, `v_station_workload`, plus role-restricted views (e.g., a public researcher view that hides sensitive operator fields).
- **Stored procedures:** `Get_Top10_Risky_Debris()`, `Fetch_Object_Lineage(catalog_id)` (recursive CTE), `Register_Satellite(...)`, `Record_Collision_Event(...)` (transactional), `Escalate_High_Risk_Events()` (uses a **cursor**).
- **Functions:** `Classify_Orbit(apogee, perigee)` returning LEO/MEO/GEO/HEO, `Risk_Level(prob, miss_distance)` using the report thresholds (miss < 1 km = high priority; prob > 1e-4 = evasive maneuver recommended).
- **Triggers:** BEFORE INSERT/UPDATE validation (negative altitude, impossible velocity, out-of-range lat/long), AFTER INSERT on COLLISION_EVENT creating an ALERT and AUDIT_LOG row when thresholds are crossed, BEFORE UPDATE on orbital elements writing the old values into ORBIT_STATE_HISTORY.
- **Transactions:** demonstrable COMMIT, ROLLBACK, and SAVEPOINT scenarios (e.g., registering a satellite plus its first conjunction events atomically, rolling back to a savepoint on failure).
- **Indexes:** meaningful B-tree and composite indexes (e.g., `(orbit_class, perigee_km)`, `(satellite_id, collision_risk_prob)`, `(event_timestamp)`, observation `(station_id, observed_at)`). Create scripts for "without index" and "with index" states so before/after `EXPLAIN` and `EXPLAIN ANALYZE` timings can be shown on a table with tens of thousands of real rows.
- **Security:** real MySQL roles and `GRANT`/`REVOKE` for `role_admin`, `role_agency`, `role_operator`, `role_researcher`, aligned with the actor-to-use-case matrix in the report. The app also enforces roles at the API level.
- **Backup and recovery:** `scripts/backup.sh` (mysqldump), `scripts/restore.sh`, and documentation of binary-log point-in-time recovery. Admin UI button to trigger a backup and list backup files.
- **Scalability (report Section 8.4):** implement MySQL table partitioning on the largest history tables (`OBSERVATION`, `ORBIT_STATE_HISTORY`), e.g., by observation year or orbit class, respecting MySQL's rule that the partition key must be part of every unique key. Show a partition-pruning `EXPLAIN` demo. Document read-replica scaling and replication/failover as an architecture explanation with a diagram (explain it; don't fake a cluster).
- **Ingestion throughput (report Section 8.1):** bulk loads use batched inserts, and a benchmark script measures rows per second and confirms concurrent reads are not blocked. Report the real numbers on the Testing page.

Organize SQL in `/db`: `01_schema.sql`, `02_constraints_indexes.sql`, `03_views.sql`, `04_functions.sql`, `05_procedures.sql`, `06_triggers.sql`, `07_roles.sql`, `08_demo_transactions.sql`, `09_index_benchmark.sql`, plus ingestion/seed scripts that load only real data.
