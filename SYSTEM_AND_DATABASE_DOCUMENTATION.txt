1. PROJECT MISSION & PROBLEM CONTEXT (KESSLER SYNDROME & ASTRODYNAMICS)
================================================================================
Since the launch of Sputnik 1 in 1957, humanity has launched over 16,000 satellites
into Earth orbit. As of 2026, the space environment is severely congested. More than
40,000 tracked artificial objects larger than 10 cm, over 1,000,000 fragments between
1 cm and 10 cm, and hundreds of millions of millimeter-sized particles populate
Low Earth Orbit (LEO, 200–2,000 km altitude).

Because orbital mechanics dictates velocities of 7.5 to 8.0 km/s in LEO, relative
closing encounter speeds during orbital intersections reach 14.0 to 15.0 km/s.
The kinetic energy governing hypervelocity collisions scales with the square of velocity:
   Ek = 0.5 * m * v^2

Under this physical reality:
- A 100-gram aluminum bolt traveling at 7.5 km/s carries 2.81 MegaJoules of kinetic energy.
- This is equivalent to detonating 0.67 kg of TNT upon structural impact.
- An impact at this velocity completely vaporizes and shatters an operational payload,
  producing a debris cloud of thousands of secondary fragments.

The Kessler Syndrome (hypothesized by NASA astrophysicist Donald J. Kessler in 1978)
describes a self-sustaining collisional cascade: once orbital debris density exceeds
a critical spatial threshold, collisions generate debris clouds that trigger further
collisions, rendering vital Sun-synchronous and low-inclination LEO bands impassable
for centuries.

ORBITWATCH solves this challenge by serving as an end-to-end, production-grade Space
Situational Awareness (SSA) platform backed by a mathematically rigorous, BCNF-normalized
MySQL 8.0 database that continuously tracks real orbital objects, assesses real close
approaches, monitors solar space weather drag, and logs sensor telemetry.

2.4 3D Globe Graphics Engine & Real-Time Coordinate Projection
--------------------------------------------------------------
The central 3D visualization is built with Three.js (WebGL):
- Earth Globe Sphere: Geometry: `SphereGeometry(1.0, 64, 64)`.
  * Shaded with a custom GLSL vertex and fragment shader (`EarthShader.ts`).
  * Procedural fractal Brownian motion (fBm) continent masks, specular ocean glints,
    sun terminator illumination, and warm amber atmospheric rim glow.
- Space Objects Particle Buffer:
  * Uses a single `THREE.Points` GPU-instanced buffer geometry supporting up to 5,000 objects.
  * Every frame, the simulation updates the float buffer arrays (`position`, `color`, `size`)
    in memory and marks attributes as `needsUpdate = true`.
- Keplerian Coordinate Propagation Math:
  Given Mean Motion n (revs/day), inclination i, eccentricity e, RAAN Omega, and
  argument of pericenter omega:
    1. Mean angular speed: n_rad = (n * 2 * PI) / 86400
    2. Mean Anomaly at time t: M(t) = M_0 + n_rad * (t - t_0)
    3. Scaled orbit radius in scene units: r_scene = (R_Earth + altitude_km) / R_Earth
    4. Orbital plane coordinates:
       x_orb = r_scene * cos(omega + M)
       y_orb = r_scene * sin(omega + M)
    5. Rotation into Earth-Centered Inertial (ECI) 3D Cartesian coordinates:
       X = x_orb * cos(Omega) - y_orb * cos(i) * sin(Omega)
       Z = x_orb * sin(Omega) + y_orb * cos(i) * cos(Omega)
       Y = y_orb * sin(i)
- Ground Station Geolocation Math:
  Given latitude lat and longitude lon in degrees:
    phi = (90 - lat) * (PI / 180)
    theta = (lon + 180) * (PI / 180)
    X = -(R * sin(phi) * cos(theta))
    Z = R * sin(phi) * sin(theta)
    Y = R * cos(phi)

3. BACKEND SERVICE ARCHITECTURE & DATA INGESTION PIPELINE
================================================================================

3.1 REST API Architecture & Security Layer
------------------------------------------
- Runtime: Node.js v20.x, Express 4.x, TypeScript 5.x.
- Database Driver: `mysql2/promise` utilizing an optimized connection pool
  (`connectionLimit: 20`, named placeholders enabled).
- Dual-Layer Security:
  1. API Layer: JWT session authentication (`jsonwebtoken`, `bcryptjs` password hashing).
     Rate limiting on authentication routes (100 requests / 15 minutes).
     Helmet security headers and CORS protection.
  2. Database Layer: MySQL native roles with explicit GRANT / REVOKE rules.
- Input Validation: Strict Zod schema validation on all POST/PUT endpoints.
- Error Handling: Centralized error middleware mapping MySQL error codes (ER_DUP_ENTRY,
  ER_NO_REFERENCED_ROW, trigger SIGNAL 45000) to clear JSON messages with zero stack trace leakage.
- Unified Deployment: In production mode (`NODE_ENV=production`), Express automatically serves
  the compiled React production bundle from `client/dist/` at `/` and handles API routes at `/api/`.

3.2 External Data Source Integrations
-------------------------------------
1. CelesTrak GP/OMM Feed (`https://celestrak.org/NORAD/elements/gp.php`):
   - Ingests General Perturbations (GP) orbital elements in JSON format.
   - Fetches active constellations and specific debris breakup groups:
     * `fengyun-1c-debris` (1,979 fragments from 2007 ASAT test)
     * `cosmos-2251-debris` (588 fragments from 2009 collision)
     * `iridium-33-debris` (109 fragments from 2009 collision)
     * `cosmos-1408-debris` (fragments from 2021 ASAT test)
2. CelesTrak SOCRATES Conjunction Feed (`https://celestrak.org/SOCRATES/sort-minRange.csv`):
   - Ingests real predicted satellite-debris conjunctions sorted by closest approach range.
   - Parses RFC 4180 CSV containing: `NORAD_CAT_ID_1`, `OBJECT_NAME_1`, `NORAD_CAT_ID_2`,
     `OBJECT_NAME_2`, `TCA` (Time of Closest Approach), `TCA_RANGE` (miss distance in km),
     `TCA_RELATIVE_SPEED` (km/s), and `MAX_PROB`.
3. NOAA Space Weather Prediction Center (`https://services.swpc.noaa.gov/`):
   - Ingests 3-hourly Planetary Kp index, 10 cm solar radio flux (F10.7), solar wind proton speed,
     and GOES-18 Primary X-ray flux.
4. NASA Near-Earth Object Web Service (`https://api.nasa.gov/neo/rest/v1/feed`):
   - Ingests live near-Earth asteroid flybys with close approach timestamps, miss distances,
     and estimated physical diameters.

3.3 Real-Time Synchronization Engine
------------------------------------
- Automated Background Cron: Scheduled via `node-cron` every 6 hours (`0 */6 * * *`) to fetch
  fresh space weather and conjunctions.
- Fast Live Sync Engine (`server/src/services/liveSync.ts`):
  * Triggered via the top navigation "SYNC LIVE APIS" button.
  * Runs parallel asynchronous fetches with a strict 3.5-second timeout for space weather and
    asteroid encounters, recalculates LEO orbital node intersections, and logs runs in `DATA_SYNC_LOG`.
- Self-Bootstrapping Database Migration (`server/src/services/autoMigrate.ts`):
  * Upon initial deployment to a fresh cloud MySQL instance (e.g. Railway or Render), the server
    checks if `SATELLITE` exists. If the database is blank, it automatically executes the schema
    scripts in `/db`, seeds roles and users, and imports the real snapshot data in seconds.

4.1 Relational Data Dictionary (All 16 Tables)
----------------------------------------------

1. Table: TRACKING_STATION
   Description: Ground surveillance radar observatories, optical telescopes, and SSA control centres.
   Columns:
   - Station_ID (INT, PK, AUTO_INCREMENT): Surrogate primary key.
   - Station_Name (VARCHAR(150), NOT NULL): Official facility name.
   - Location_Country (VARCHAR(100), NOT NULL): Host country / territory.
   - Latitude (DECIMAL(8,4), NOT NULL): Latitude in degrees, CHECK (Latitude BETWEEN -90.0 AND 90.0).
   - Longitude (DECIMAL(8,4), NOT NULL): Longitude in degrees, CHECK (Longitude BETWEEN -180.0 AND 180.0).
   - Sensor_Type (VARCHAR(100), NOT NULL): Radar or optical sensor classification.
   - source_url (VARCHAR(255), NULL): Reference agency verification link.
   - created_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP).

2. Table: SATELLITE
   Description: Operational and defunct payloads tracked by international space surveillance networks.
   Columns:
   - Satellite_ID (INT, PK, AUTO_INCREMENT): Surrogate primary key.
   - NORAD_ID (INT, NOT NULL, UNIQUE): Official North American Aerospace Defense Command catalog ID.
   - intl_designator (VARCHAR(50), NOT NULL, UNIQUE): International COSPAR identifier (e.g. 1998-067A).
   - Satellite_Name (VARCHAR(150), NOT NULL): Common spacecraft name.
   - Owner_Agency (VARCHAR(100), NOT NULL): Operating space agency or commercial constellation operator.
   - Launch_Date (DATE, NULL): Date of orbital insertion.
   - Operational_Status (ENUM('Active','Inactive','Deorbiting','Destroyed'), NOT NULL, DEFAULT 'Active').
   - Orbital_Altitude_KM (DOUBLE, NOT NULL): Mean orbital altitude, CHECK (Orbital_Altitude_KM > 0).
   - Inclination_Deg (DOUBLE, NOT NULL): Orbital inclination, CHECK (Inclination_Deg BETWEEN 0.0 AND 180.0).
   - Apogee_KM (DOUBLE, NOT NULL): Highest orbital altitude, CHECK (Apogee_KM >= 0).
   - Perigee_KM (DOUBLE, NOT NULL): Lowest orbital altitude, CHECK (Perigee_KM >= 0).
   - Eccentricity (DOUBLE, NOT NULL, DEFAULT 0.001, CHECK Eccentricity >= 0.0).
   - Mean_Motion (DOUBLE, NOT NULL, DEFAULT 14.0, CHECK Mean_Motion > 0.0): Revolutions per day.
   - RAAN (DOUBLE, NOT NULL, DEFAULT 0.0, CHECK RAAN BETWEEN 0.0 AND 360.0): Right Ascension of Ascending Node.
   - Arg_Pericenter (DOUBLE, NOT NULL, DEFAULT 0.0, CHECK Arg_Pericenter BETWEEN 0.0 AND 360.0).
   - Mean_Anomaly (DOUBLE, NOT NULL, DEFAULT 0.0, CHECK Mean_Anomaly BETWEEN 0.0 AND 360.0).
   - BSTAR (DOUBLE, NOT NULL, DEFAULT 0.0): SGP4 atmospheric drag term.
   - Epoch (DATETIME, NOT NULL): UTC timestamp of orbital element set.
   - orbit_class (ENUM('LEO','MEO','GEO','HEO'), NOT NULL, DEFAULT 'LEO').
   - source (VARCHAR(50), DEFAULT 'CelesTrak').
   - ingested_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP).
   - updated_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP).

3. Table: DEBRIS
   Description: Tracked fragmentation debris, spent rocket bodies, and mission-related debris.
   Columns:
   - Debris_ID (INT, PK, AUTO_INCREMENT): Surrogate primary key.

4.3 Stored Procedures & Recursive Graph Traversal (5 Procedures)
----------------------------------------------------------------
1. `Get_Top10_Risky_Debris()`:
   - Aggregates conjunction encounters by debris object, returning the top 10 fragments
     posing the greatest collision hazard ordered by `MAX(Collision_Risk_Prob) DESC` and
     `MIN(Miss_Distance_KM) ASC`.
2. `Fetch_Object_Lineage(IN p_catalog_id INT)` (Recursive CTE):
   - Implements a Recursive Common Table Expression traversing parent-child debris breakups:
     WITH RECURSIVE DebrisTree AS (
       -- Anchor Member: direct fragments matching root parent NORAD ID
       SELECT l.Lineage_ID, l.fragment_debris_id, d.NORAD_ID AS fragment_norad_id,
              d.Object_Name AS Fragment_Name, l.parent_catalog_id, l.parent_name,
              l.breakup_event_name, l.breakup_date, l.event_type, 1 AS Generation_Level
       FROM DEBRIS_LINEAGE l
       JOIN DEBRIS d ON l.fragment_debris_id = d.Debris_ID
       WHERE l.parent_catalog_id = p_catalog_id OR d.NORAD_ID = p_catalog_id

       UNION ALL

       -- Recursive Member: child sub-fragments of previous generation fragments
       SELECT sub_l.Lineage_ID, sub_l.fragment_debris_id, sub_d.NORAD_ID,
              sub_d.Object_Name, sub_l.parent_catalog_id, sub_l.parent_name,
              sub_l.breakup_event_name, sub_l.breakup_date, sub_l.event_type,
              dt.Generation_Level + 1
       FROM DEBRIS_LINEAGE sub_l
       JOIN DEBRIS sub_d ON sub_l.fragment_debris_id = sub_d.Debris_ID
       JOIN DebrisTree dt ON sub_l.parent_catalog_id = dt.fragment_norad_id
       WHERE dt.Generation_Level < 3
     )
     SELECT * FROM DebrisTree ORDER BY Generation_Level ASC, breakup_date DESC LIMIT 100;
3. `Register_Satellite(...)`:
   - Transactional stored procedure that validates altitude and inclination bounds, deterministically
     evaluates `Classify_Orbit(apogee, perigee)`, inserts the satellite, and writes an audit row
     into `AUDIT_LOG` inside a single ACID `START TRANSACTION` / `COMMIT` block.
4. `Record_Collision_Event(...)`:
   - Evaluates conjunction severity via `Risk_Level(prob, miss_dist)` and commits the encounter.
5. `Escalate_High_Risk_Events()` (Explicit MySQL CURSOR):
   - Declares an explicit MySQL cursor: `DECLARE cur_high_risk CURSOR FOR ...`
   - Iterates row-by-row over open high-risk conjunction encounters occurring within the next 48 hours
     where miss distance <= 1.0 km or collision probability >= 1e-4.
   - For every qualifying encounter, creates an emergency record in `ALERT` with `status = 'ACTIVE'`
     and logs the escalation in `AUDIT_LOG`.

4.4 Deterministic Scalar Functions (4 Functions)
------------------------------------------------
1. `Classify_Orbit(p_apogee DOUBLE, p_perigee DOUBLE) RETURNS VARCHAR(10)`:
   - Evaluates orbital altitude regime:
     * GEO: perigee >= 35,000 km, apogee <= 36,500 km, abs(apogee - perigee) < 1,000 km.
     * HEO: apogee >= 36,000 km or (apogee - perigee >= 10,000 km and apogee > 5,000 km).
     * LEO: apogee < 2,000 km and perigee < 2,000 km.
     * MEO: perigee >= 2,000 km and apogee < 36,000 km.
2. `Risk_Level(p_prob DOUBLE, p_miss_distance DOUBLE) RETURNS VARCHAR(20)`:
   - Aligned with NASA CARA (Conjunction Assessment Risk Analysis) thresholds:
     * CRITICAL: Miss Distance <= 1.0 km OR Collision Probability >= 10^-4.
     * WARNING: Miss Distance <= 5.0 km OR Collision Probability >= 10^-5.
     * MONITOR: Miss Distance <= 25.0 km.
     * NOMINAL: Miss Distance > 25.0 km.
3. `Calculate_Kinetic_Energy(p_mass_kg DOUBLE, p_velocity_kms DOUBLE) RETURNS DOUBLE`:
   - Calculates kinetic impact energy in MegaJoules (MJ): Ek = 0.5 * m * (v * 1000)^2 / 1,000,000.
4. `Calculate_Semi_Major_Axis(p_mean_motion DOUBLE) RETURNS DOUBLE`:
   - Derives orbital semi-major axis (km) from mean motion n (revs/day) via Kepler's Third Law:
     a = (mu / n_rad^2)^(1/3), where mu = 398600.4418 km^3/s^2.

4.5 Database Integrity & Automation Triggers (5 Triggers)
---------------------------------------------------------
1. `trg_validate_satellite_before_insert` (BEFORE INSERT ON SATELLITE):
   - Prevents unphysical records at the database engine level. Rejects the transaction with
     `SIGNAL SQLSTATE '45000'` if `Orbital_Altitude_KM <= 0`, `Inclination_Deg < 0 OR > 180`,
     or `Perigee_KM > Apogee_KM`.
2. `trg_validate_debris_before_insert` (BEFORE INSERT ON DEBRIS):
   - Rejects unphysical velocity (`Velocity_KMS <= 0 OR > 15.0`) or `Perigee_KM > Apogee_KM`
     with `SIGNAL SQLSTATE '45000'`.
3. `trg_collision_event_after_insert` (AFTER INSERT ON COLLISION_EVENT):
   - Automated event-driven alerting: whenever an encounter with `risk_level IN ('CRITICAL', 'WARNING')`
     or `Miss_Distance_KM <= 1.0` is inserted, automatically inserts an emergency alert row into
     `ALERT` and creates a non-repudiation entry in `AUDIT_LOG`.
4. `trg_satellite_orbit_history_before_update` (BEFORE UPDATE ON SATELLITE):
   - Trajectory versioning: if inclination, apogee, perigee, or mean motion changes, archives the
     previous orbital state into `ORBIT_STATE_HISTORY` before applying the update.
5. `trg_debris_orbit_history_before_update` (BEFORE UPDATE ON DEBRIS):
   - Archives previous debris trajectory parameters into `ORBIT_STATE_HISTORY` upon modification.

4.6 MySQL Range Table Partitioning & Partition Pruning
------------------------------------------------------
The `OBSERVATION` table is range-partitioned on `YEAR(observed_at)`:
   PARTITION BY RANGE (YEAR(observed_at)) (
       PARTITION p2024 VALUES LESS THAN (2025),
       PARTITION p2025 VALUES LESS THAN (2026),
       PARTITION p2026 VALUES LESS THAN (2027),
       PARTITION p2027 VALUES LESS THAN (2028),
       PARTITION p_future VALUES LESS THAN MAXVALUE
   );

Proof of Partition Pruning:
When querying passes for the current year:
   EXPLAIN SELECT * FROM OBSERVATION WHERE observed_at BETWEEN '2026-01-01' AND '2026-12-31';

The MySQL optimizer returns:
   table: observation | partitions: p2026 | type: ALL | rows: 40

The `partitions` column confirms that MySQL scans strictly partition `p2026` from disk,
completely pruning partitions `p2024`, `p2025`, `p2027`, and `p_future`.

*Engine Note on Partitioning vs. Foreign Keys:*
MySQL 8.x error 1506 (`ERROR 1506 (HY000): Foreign keys are not yet supported in conjunction with
partitioning`) disallows foreign key constraints on partitioned tables. Referential integrity on
`OBSERVATION.Station_ID` is enforced via high-performance B-tree indexes and application logic.

4.9 ACID Transaction Management (COMMIT, SAVEPOINT, ROLLBACK)
-------------------------------------------------------------
1. Atomicity (COMMIT):
   START TRANSACTION;
   INSERT INTO SATELLITE (...) VALUES (...);
   SET @new_sat_id = LAST_INSERT_ID();
   INSERT INTO OBSERVATION (Station_ID, Satellite_ID, ...) VALUES (8, @new_sat_id, ...);
   COMMIT;
   Both the satellite and its observation pass are guaranteed to commit together atomically.

2. Partial Failure Recovery (SAVEPOINT & ROLLBACK TO SAVEPOINT):
   START TRANSACTION;
   INSERT INTO SATELLITE (...) VALUES (...);
   SAVEPOINT SatelliteCreated;
   -- Secondary pass attempts invalid insert or encounters an application error:
   ROLLBACK TO SAVEPOINT SatelliteCreated;
   -- Valid secondary pass is inserted:
   INSERT INTO OBSERVATION (Station_ID, Satellite_ID, ...) VALUES (7, @new_sat_id, ...);
   COMMIT;
   Recovers from auxiliary failures without aborting the expensive primary satellite registration.

3. Complete Abort (ROLLBACK):
   START TRANSACTION;
   INSERT INTO SATELLITE (...) VALUES (88803, 'DOOMED-SAT', ...);
   ROLLBACK;
   A follow-up query confirms that 0 rows exist for NORAD ID 88803.

4.10 Formal Boyce-Codd Normal Form (BCNF) Mathematical Proof
------------------------------------------------------------
A relational schema R is in Boyce-Codd Normal Form (BCNF) if and only if, for every
non-trivial functional dependency X -> Y in F+, X is a superkey of R.

1. Table: TRACKING_STATION
   - Primary Key: Station_ID
   - Candidate Keys: {Station_ID}
   - Non-trivial FDs: Station_ID -> Station_Name, Location_Country, Latitude, Longitude, Sensor_Type
   - Proof: The determinant {Station_ID} is a candidate key. No non-superkey determinants exist.
   - Status: BCNF Satisfied.

2. Table: SATELLITE
   - Primary Key: Satellite_ID
   - Candidate Keys: {Satellite_ID}, {NORAD_ID}, {intl_designator}
   - Non-trivial FDs:
     * Satellite_ID -> NORAD_ID, intl_designator, Satellite_Name, Owner_Agency, Orbital_Altitude_KM...
     * NORAD_ID -> Satellite_ID, intl_designator, Satellite_Name, Owner_Agency...
     * intl_designator -> Satellite_ID, NORAD_ID, Satellite_Name...
   - Proof: Every determinant is a candidate key (and thus a superkey). There are no partial
     dependencies and no transitive dependencies.
   - Status: BCNF Satisfied.

3. Table: DEBRIS
   - Primary Key: Debris_ID
   - Candidate Keys: {Debris_ID}, {NORAD_ID}
   - Non-trivial FDs:
     * Debris_ID -> NORAD_ID, Object_Name, Size_Meters, Velocity_KMS, Apogee_KM, Perigee_KM...
     * NORAD_ID -> Debris_ID, Object_Name, Size_Meters...
   - Proof: Every determinant is a candidate key and superkey.
   - Status: BCNF Satisfied.

4. Table: COLLISION_EVENT

   - Candidate Keys: {Event_ID}, {Satellite_ID, Debris_ID, Event_Timestamp}
   - Non-trivial FDs:
     * Event_ID -> Satellite_ID, Debris_ID, Event_Timestamp, Miss_Distance_KM, Collision_Risk_Prob...
     * {Satellite_ID, Debris_ID, Event_Timestamp} -> Event_ID, Miss_Distance_KM, Collision_Risk_Prob...
   - Proof: Both determinants are candidate keys and superkeys.
   - Status: BCNF Satisfied.

5. Table: OBSERVATION
